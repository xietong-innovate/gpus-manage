1 背景与目标

1.1 现状与问题

OpenPAI 是微软开源的完整 AI 平台，围绕"作业（Job）"组织能力：作业提交与排队、Jupyter 交互开发、用户/组/配额管理，以及基于监控组件的集群指标。它解决的是"平台代管任务"的场景。

但在高校实验室与中型研发团队的真实运转中，还存在一个 OpenPAI 未直接覆盖的场景：用户绕过平台、直接在 GPU 机器上运行任务。典型表现为：

  • 用户通过终端登录 GPU 机器，在自己熟悉的 conda / venv 虚拟环境中直接启动训练脚本，而非向平台提交作业；
  • 任务长期占用显卡、训练结束后忘记释放，管理员需要逐台登录机器才能知道"这张卡现在谁在用、跑在哪个环境、占了多少显存"；
  • 发现违规占用后，缺少一个受控的、有留痕的一键终止入口，只能手动逐台处理；
  • 新采购或新上架的 GPU 机器，接入集群缺少一个统一的资产登记动作，卡数、型号、显存规格全靠人工记录。
核心矛盾 OpenPAI 以"作业"为中心，而实验室日常管理需要以"显卡"为中心：管理员视角下的最小问题不是"作业排队多久"，而是"这张卡现在被谁、用哪个环境、占了多少显存，以及我能不能立刻释放它"。

1.2 产品决策

在 OpenPAI 现有代码基础上深度魔改，将产品重心从"作业调度平台"改造为"GPU 资产管理与实时管控系统"：节点批量接入、显卡级实时监控、进程归属与虚拟环境追踪、管理员高权限终止控制，全程审计留痕。原 OpenPAI 的作业提交/Jupyter 等能力与本次改造的关系见 第 8 节开放问题 Q1。

1.3 目标（以可观察行为表述）

目标可观察的完成证据
裸 IP 清单一键变为受管资产管理员粘贴一批 IP 并提交后，全部可达节点自动登记入册，且每台节点的显卡（型号、总显存、序号）被自动发现并出现在总览页；失败的 IP 逐条给出失败原因。
每张显卡实时可见总览页在 5 秒 采集/刷新周期内反映每张卡的状态、已用显存、总显存、利用率与温度；节点失联时卡片明确显示"状态未知"，不展示过期数据冒充实时数据。
占用可追责到"人 + 环境"点击任意显卡可看到其上每个进程的 PID、属主用户、来源 Python 虚拟环境名、显存占用与运行时长；卡级显存与进程级显存的差额以"其他/系统占用"单独列示。
高权限终止受控且留痕管理员可对任意在线显卡上的任意进程发起终止：系统强制二次确认（输入目标 PID）并要求填写原因，先优雅终止、宽限期 30 秒 后强制终止；结果即时反馈并写入不可删改的审计记录。

注：TBD 标记为本文档给出的默认值，允许在评审时修改；修改后即为该规则的唯一口径（见第 6 节）。

2 产品契约

要素定义
主要用户实验室 / 团队的 GPU 管理员（对全部 GPU 资产与进程拥有最高权限的运维角色）。普通用户自助视图为 P1（FR-9）。
触发场景① 新机器上架，管理员拿到一批裸 IP 清单；② 例行巡检"哪些卡空着"；③ 接到"某卡被长期占用/疑似异常进程"的投诉，需要定位并处理。
核心任务（P0 旅程）绑定节点 → 总览看到每张卡的实时状态与显存 → 下钻看到占用进程及其虚拟环境归属 → 确认后终止违规进程 → 全程可审计回溯。
完成证据节点与显卡出现在总览；终止指令发出后目标进程从卡上消失、已用显存回落、审计记录出现对应条目。
共享业务对象GPU 节点（机器）、显卡、进程、审计记录。定义与字段见第 4 节。
信任与风险规则终止他人进程、删除节点均属不可逆高危操作：一律强制二次确认 + 原因必填 + 审计留痕（FR-4、FR-5、第 6.5 节）。

3 范围与优先级

3.1 最小完整旅程（P0）

入场：管理员首次部署时创建管理员账号（FR-4），登录系统。
接入：粘贴/批量录入全部 GPU 节点 IP，系统校验并自动发现每节点显卡清单（FR-1）。
观测：总览页实时看到每张卡的状态、已用/总显存、利用率、温度（FR-2）。
下钻：点击显卡查看占用进程、属主、Python 虚拟环境、显存占用（FR-3）。
处置：对违规进程走"二次确认 + 原因必填 → 优雅终止 → 宽限强杀"流程（FR-4）。
回溯：任何时刻可在审计页查到"谁在何时终止了谁的黑匣子记录"（FR-5）。
恢复：接入失败的 IP 可修正后重试（FR-1）；节点失联自动转"离线"并在恢复后自动回"在线"（第 6.3 节），无需人工重新绑定。

3.2 优先级划分

级别内容理由
P0 首版必交付FR-1 节点接入管理、FR-2 显卡实时监控、FR-3 进程与虚拟环境追踪、FR-4 管理员认证与终止控制、FR-5 审计日志四项原始需求 + 审计。审计被列为 P0 的理由：终止他人进程属不可逆高风险操作，无留痕则该功能不应上线（产品判断）。
P1 第一轮迭代FR-6 告警与通知、FR-7 统计报表、FR-8 硬件健康监控、FR-9 普通用户自助视图共享集群进入"多用户共治"阶段后成为刚需，但不阻塞首版核心旅程。
P2 远期规划FR-10 GPU 预约与配额、FR-11 异常进程检测、FR-12 开放 API依赖 P1 数据积累或组织规则成熟后才有意义。

3.3 明确不做（首版排除）

  • 不重建作业调度器：不开发新的作业排队/调度内核；OpenPAI 原有调度能力是否保留见开放问题 Q1，首版按"不依赖其运行"设计。
  • 不做远程文件管理 / 代码编辑器：不属于"卡资产管理"旅程。
  • 不做显卡资源虚拟化/切分（如 MIG 细粒度划分的自动化编排）：仅只读展示厂商已有的切分信息（如有）。
  • 不承诺跨网段 / NAT 穿透：首版假设全部节点与管理系统网络互通 假设。

4 角色与对象模型

4.1 角色与权限矩阵

首版只有一个显式角色（管理员）。矩阵同时给出 P1 引入普通用户后的目标态，避免首版设计堵死演进路径。

操作管理员（P0）普通用户（P1 目标态）
批量绑定 / 新增 / 删除 / 维护节点允许禁止
查看全部显卡实时状态与占用明细允许允许只读（是否开放全部卡给所有登录用户：待定，默认开放总览、明细仅限本人占用的卡）
终止进程任意进程仅本人属主的进程
查看审计日志全部记录仅与自己相关的记录
告警规则管理（FR-6）允许禁止
管理员账号管理（增删管理员、重置密码）允许（须 Existing 管理员执行，见 4.4）禁止

4.2 对象模型

对象关键字段说明
GPU 节点
绑定/IP 管理的真正对象		节点名（可改）、IP、端口、访问凭据（加密存储、永不明文回显）、分组标签、状态、接入时间、显卡数、驱动版本、最后心跳时间一台物理机一个 IP；"显卡的 IP"在物理上不可分——IP 挂在节点上，显卡随节点接入后自动逐张发现并登记。
显卡GPU 索引、型号、总显存(MB)、UUID、所属节点、当前已用显存(MB)、利用率(%)、温度、功耗、状态总显存、型号、UUID 在节点接入时固化登记，不随后续热插拔静默变化；如检测到与登记不符（换卡），标记"硬件变更"提示管理员确认（异常态，见 6.6）。
进程PID、属主用户（节点系统用户名）、可执行名、命令行摘要、虚拟环境名、环境类型、显存占用(MB)、启动时间、运行时长、状态同一节点内 PID 唯一定位；跨节点须以"节点 + PID"联合定位。

4.3 状态机

节点状态

状态进入条件允许的操作
接入验证中管理员提交绑定后查看进度；失败后修正重试
在线验证通过且心跳正常全部操作
离线连续 3 个采集周期无心跳可删除（其卡显示"状态未知"）；不可发起进程终止
维护中管理员手动设置（如升级驱动）不参与空闲统计、不接收新告警；可恢复在线

状态迁移：验证中 →（通过）在线 / （失败）接入失败（终态，可重试）；在线 ⇄ 离线（自动双向）；在线 ⇄ 维护中（手动双向）。

显卡状态

状态判定规则（唯一口径）
空闲卡上无运行中的受管进程，且已用显存 ≤ 500 MB（驱动基础占用阈值，可配置）
占用中存在至少一个运行中的占用进程
故障驱动上报错误（如 ECC 错误、掉卡）或采集持续异常
状态未知所属节点离线/维护中——绝不沿用旧数据，界面必须显示未知而非最后一次快照

"占用中"与"空闲"互斥且由 6.1 节口径唯一计算；"空闲但显存异常高"（无进程却 >阈值）单独提示为疑似泄漏，状态仍为空闲并附黄色警示角标。

进程状态：运行中 →（优雅终止退出）已退出 /（宽限期超时被强杀）已强制终止 /（期间自行退出）已自行退出。终态进程保留展示 10 分钟 后从实时视图消失。

4.4 管理员账号规则

  • 首次创建：首次部署进入引导页，强制创建首个管理员（用户名 + 密码 + 确认密码）；创建完成前系统拒绝任何其他操作 假设：无内置默认口令，避免弱口令上线。
  • 多管理员：允许存在多名管理员；任何在职管理员可新增/停用其他管理员账号，停用自己需要另一名管理员确认 待定：是否限制最少保留 1 名。
  • 密码策略：最小长度 10 位，须含字母与数字；修改密码须验证旧密码；连续失败 5 次锁定 15 分钟；会话闲置 12 小时 过期（均可配置）。
  • 敏感数据边界：节点访问凭据仅写入加密存储，任何界面与接口不回显明文，仅显示"已配置/未配置"。

5 功能需求

以下 FR-1 ~ FR-4 逐条覆盖四项原始需求；FR-5 起为补充能力（对应用户提出的"遗漏功能"问题，汇总见第 7 节）。每个模块按：目的 → 触发 → 处理规则 → 结果与状态变化 → 异常展开。

FR-1GPU 节点接入管理 P0

目的：让管理员用一次操作把全部 GPU 机器登记入册，并自动获得每台机器的显卡资产清单；支持后续增删。

FR-1.1 批量绑定（对应原始需求 1）

项规则
触发管理员在"节点管理"页点击【批量绑定】，进入录入界面。
录入方式① 文本框粘贴多行，每行 IP 或 IP:端口（端口缺省用凭据中的默认端口）；② 上传 CSV/TXT 文件，格式同 ①。
格式校验仅支持 IPv4 假设：实验室为内网 IPv4；非法行、重复行、与已绑定节点冲突的行不阻断整批，逐行标注后跳过。
访问凭据整批共用一套节点凭据（用户名 + 密码/密钥）；绑定成功后可对单节点单独替换（FR-1.4）。
接入验证（逐节点）绑定即验证，逐台展示四步进度：① 网络可达 → ② 可登录 → ③ 可采集 GPU 清单 → ④ 登记显卡资产。任意一步失败即停止后续步骤并给出该步的失败原因。
显卡自动发现步骤 ③ 通过后，系统读取该节点显卡清单：GPU 索引、型号、总显存、UUID，固化为显卡档案；卡数以实际发现为准，不要求管理员填写。
结果与状态全部行处理完毕后显示汇总：成功 N 台、失败 M 台、跳过 K 条；成功节点状态转"在线"，失败行可修正后重试。
产品判断：绑定对象是"节点"而非"显卡" 原始需求表述为"把所有 GPU 显卡的 IP 绑定至系统"。一张显卡没有独立 IP，IP 属于机器；一台机器可插 1~N 张卡。因此本系统把 IP 绑定在节点层，显卡在节点接入成功后自动逐张发现登记——管理员永远不需要手工录卡。

FR-1.2 新增单个节点

入口与交互同批量绑定，仅一次处理一行；适用于零星扩容。

FR-1.3 删除节点

项规则
触发节点行【删除】按钮。
默认阻止若节点在线且其显卡上存在运行中的占用进程，删除被阻止，弹窗列出受影响进程（属主、PID、显存）。
强制下线弹窗内提供"强制终止该节点全部进程并删除"复选框；勾选后须输入节点 IP 文本确认方可执行。强制路径同样走 FR-4 的优雅终止 → 宽限 → 强杀规则，并逐条写审计。
离线节点离线节点删除不受进程阻止（进程状态本已不可控），但须输入 IP 确认。
删除后果节点与其显卡从实时视图与统计中消失；历史数据（报表、审计）中的既有记录保留该节点标识。删除不可撤销；重新绑定同 IP 视为全新节点（显卡档案重建）。

FR-1.4 节点维护

  • 可编辑：节点名、分组标签、访问凭据（凭据变更后立即做一次连通验证）。
  • 维护模式：置为"维护中"后，该节点不参与空闲率统计、不产生离线告警（FR-6），其卡显示"状态未知"。

FR-1.5 异常与边界

  • 同一 IP 重复绑定：粘贴清单内部重复 → 后行标"重复，跳过"；与已绑定节点重复 → 标"已存在，跳过"。不创建重复档案。
  • 接入验证超时单步 15 秒；整批并行验证，单台失败不影响其他台。
  • 绑定后立即失联（验证通过但首个心跳即失败）：节点保留"在线"直至心跳超时规则（6.3）生效转"离线"，并给出"该节点接入后未上报心跳"的显式提示。
  • 显卡档案与实际不符（换卡/加减卡）：出现"硬件变更"告警，管理员确认后更新档案；未确认前以"状态未知"呈现变动卡位。
交互演示 D1 — 批量绑定 / 校验 / 删除（对应 FR-1，可在页面上直接操作）
演示数据：lab-a 在线 4 卡；lab-b 在线 4 卡且 GPU0 有占用进程（用于体验"删除被阻止"）
节点名IP:端口分组显卡驱动最后心跳状态操作
还没有任何节点。点击"批量绑定节点"录入首批 GPU 机器。

FR-2显卡实时监控总览 P0

目的（对应原始需求 2）：管理员打开系统第一眼即回答"现在哪些卡空着、哪些卡被占、占了多少、卡本身多大"。

项规则
触发与布局登录后默认页。顶部汇总条 + 按节点分组的显卡卡片矩阵。每卡展示：节点名+GPU 索引、型号、状态色标、已用显存 / 总显存（数字 + 进度条）、利用率、温度、占用进程数。
汇总条总卡数、空闲 / 占用中 / 故障 / 状态未知分项计数，总显存与已用显存合计，空闲率。
实时口径采集周期默认 5 秒（可配置 1–60 秒）；页面自动刷新同频，可手动暂停/恢复。超过 2 个周期未更新时页面顶部出现"数据延迟"提示条。
筛选与排序按节点分组标签筛选；按状态过滤（只看空闲 / 只看占用）；同节点内按 GPU 索引排序。
下钻点击任意"占用中"卡片展开该卡进程面板（FR-3）；点击"空闲但显存异常"卡同样展开，显示"无进程 + 疑似显存泄漏"提示。
状态渲染规则占用中（蓝/橙）、空闲（绿）、故障（红）、状态未知（灰且禁用下钻，附"节点离线"原因）。
异常与空态① 零节点：引导页指向 FR-1；② 全部离线：矩阵灰显 + "集群失联"横幅；③ 单节点离线：该组显示"心跳超时"占位条，不渲染旧数据。

FR-3进程与 Python 虚拟环境追踪 P0

目的（对应原始需求 3）：回答"这张卡上的占用进程来自哪个虚拟环境、是谁启动的、占了多少显存、跑了多久"。

项规则
触发总览页点击显卡卡片（或从告警/审计链接跳转到某卡）。
进程面板字段PID、属主用户（节点系统用户名）、可执行名 + 命令行摘要、虚拟环境徽章、显存占用(MB)、启动时间、运行时长、操作（终止，权限见 4.1）。
显存勾稽面板底部固定一行"其他/系统占用 = 卡已用显存 − Σ进程显存"。该值 ≥ 0 恒成立；若出现负数视为采集异常，显示"—"并触发数据质量提示（6.6）。

虚拟环境识别规则（全系统唯一口径，见 6.2）

进程可执行路径特征展示为示例
conda 环境目录 envs/<名称> 下的解释器conda:llm-ft（环境名）.../envs/llm-ft/bin/python → conda:llm-ft
venv / .venv / virtualenv 目录下的解释器venv:rag-eval（取虚拟环境根目录名）~/proj/rag-eval/.venv/bin/python → venv:rag-eval
系统解释器路径（无虚拟环境特征）system-python/usr/bin/python3
非 Python 可执行非Python: <可执行名>二进制、bash 子进程等

规则说明：识别依据为进程可执行路径与命令行的组合特征（产品口径）；识别在节点侧完成，仅向管理端回传解析后的环境名与路径，避免回传敏感环境变量。

异常与边界

  • 同一 PID 短时间反复出现/消失（秒级任务）：合并展示为"高频短任务"，避免面板抖动。
  • 属主为 root 或系统账户的进程：正常展示，但终止时额外警示（终止系统组件可能导致节点失联）。
  • 容器内进程 待定：首版假设进程直接运行于节点操作系统，非容器化。若存在容器化作业（OpenPAI 作业即如此），显示容器标识而非虚拟环境——见开放问题 Q1。

FR-4管理员认证与进程终止控制 P0

目的（对应原始需求 4）：以"单一最高权限角色 + 受控高危操作"的方式，让管理员能安全地终止任意显卡上的任意进程。

FR-4.1 认证与会话

  • 全部页面与接口须登录后访问；首次部署强制创建管理员（4.4）。
  • 登录/登出、密码策略、锁定与会话过期规则见 4.4；登录成功与失败均写审计（FR-5）。

FR-4.2 终止任意进程（核心高危流）

发起：进程面板点击【终止】。管理员对任意进程有终止权，无属主限制。
确认弹窗：展示目标进程完整档案（节点、GPU、PID、属主、环境、命令、显存、运行时长）；原因必填（写入审计）；须在输入框中输入目标 PID 数字，按钮方可点亮——防止误杀与"闭眼点确认"。
执行（优雅优先）：先向目标进程发送可捕获的终止信号并进入宽限期 30 秒；宽限期内界面实时显示该进程状态与倒计时。进程若自行退出（含响应信号清理后退出），流程结束，记录结果"优雅退出"。
强杀兜底：宽限期届满仍在运行 → 发送不可捕获信号强制终止，记录结果"强制终止"。
结果反馈与状态变化：成功 → 进程行转终态并淡出，卡已用显存按下一采集周期回落，审计落账；失败 → 显示具体失败原因并保留重试入口。
通知：被终止进程的属主用户收到站内通知（P1 接入邮件/Webhook，FR-6）。

FR-4.3 终止的异常分支

情形系统行为
宽限期内进程自行退出正常结束，结果记"自行退出（宽限期内）"，不重复发送强杀信号。
发起时进程已不存在提示"进程已退出"，无副作用，不写终止审计（写一条"目标已消失"的备注记录）。
执行期间节点失联终止指令结果"未知"（无法确认送达/生效），显卡转"状态未知"，审计记录该不确定性；节点恢复后以进程是否仍在来复核并补记。
终止指令失败（权限不足等）反馈失败原因；同一进程 1 分钟内最多允许重试 3 次，超出后建议管理员通过节点维护流程处理。
批量终止首版不提供跨卡多选批杀（单卡内可多选）；跨节点批量属 P1 评估项——降低误操作半径为产品判断。
交互演示 D2 — 实时总览 / 进程下钻 / 终止流程（对应 FR-2 / FR-3 / FR-4，可直接操作）
AUDIT TRAIL（本演示产生的审计记录）
演示要点：占用卡含 conda / venv / 非 Python 异常进程三种环境徽章；故障卡与离线节点展示"不沿用旧数据"的未知态；终止流程完整复现"原因必填 + 输入 PID 确认 → 优雅终止倒计时 → 强杀兜底 → 显存回落 → 审计落账"（演示中宽限期缩短为 3 秒）。

FR-5审计日志 P0

目的：原始需求未提及，但作为"管理员可终止任何人进程"这一高危能力的配套，属首版必备——没有审计的强制终止不应上线。

项规则

6 共享规则与数据口径（全系统唯一定义处）

以下规则被多个 FR 引用，任何模块不得另行定义。

6.1 显存口径

  • 卡已用显存 = 驱动上报的"已用显存总量"，包含驱动上下文与碎片开销，因此恒 ≥ Σ(进程显存)。
  • 进程显存 = 驱动按进程统计的占用值；多个进程共享同一上下文的场景允许重复计入，以驱动值为准。
  • 其他/系统占用 = 卡已用显存 − Σ(进程显存)，仅用于卡级勾稽展示，不参与任何告警阈值计算（避免负值/波动误报）。
  • 单位统一 MB 展示（<1GB 显示 MB，≥1GB 显示两位小数 GB）。

6.2 虚拟环境识别

唯一规则见 FR-3 表格；徽章文案（conda: / venv: / system-python / 非Python: / 未知）全系统统一，审计与告警复用同一解析结果。

6.3 实时性与心跳

  • 采集周期默认 5 秒；节点级心跳与指标同通道。连续 3 个周期无数据 → 节点"离线"，其卡全部转"状态未知"。
  • 节点恢复上报后自动转"在线"，无需人工干预；一次离线事件记一条审计备注（不产生告警风暴，重复离线按 FR-6 静默期规则收敛）。

6.4 宽限期与重试

  • 终止宽限期 30 秒；同一进程终止重试 1 分钟内 ≤ 3 次（FR-4.3）。
  • 接入验证单步超时 15 秒（FR-1.5）。

6.5 高危操作确认规范

操作确认方式原因审计
终止单个进程输入目标 PID必填必写（含结果）
删除节点（有活动进程）勾选强制下线 + 输入节点 IP必填必写（含被终止进程清单）
删除节点（无活动进程/离线）输入节点 IP选填必写
显卡硬件变更确认弹窗确认选填必写

6.6 数据质量与降级

  • 任何采集项失败（显存读不到、进程列表不可读）：显示"不可读"占位，不使用 0 或旧值冒充。
  • 勾稽异常（Σ进程 > 卡已用）：面板标"数据异常"并记数据质量日志，不阻断其他卡展示。
  • 时间统一为集群时区（Asia/Shanghai）。
