## 1. 背景与问题

### 1.1 现状

当前系统采用「**管理端主动拉取**」架构：

1. 管理员在页面录入 `IP` 或 `IP:端口`，系统落盘节点档案；
2. 服务端每 `5s` 对每个在线节点执行一次 SSH 命令（`nvidia-smi` 查询 + `/proc` 进程信息）；
3. 通过 SSE 把全量快照推给浏览器；
4. 终止进程时，服务端再通过同一条 SSH 通道下发两段式终止指令。

实现层面有几个与「跨网段」直接冲突的硬约束（均在代码中可验证）：

| 约束 | 位置 | 影响 |
|---|---|---|
| 连接方式由 IP 隐式推断：`ip === '127.0.0.1' \|\| 'localhost'` 即视为本机直连 | `server/collector.js` `isLocalIp()`、`server/routes/nodes.js` `createRecord()` | 反向隧道 / 端口映射场景下，节点地址可能就是 `127.0.0.1:20022`，会被误判为本机 |
| 节点以 **IP 作为全局唯一键** | `store.js`（`Map<ip, rec>`）、`state.js`（`snapshots`）、`collector.js`（`conns`）、路由 `/:ip` | 两个不同网段都存在 `192.168.1.10` 时，后绑定者会覆盖前者 |
| 无跳板机 / 代理 / 隧道概念 | `server/ssh.js` 仅支持 `host + port` 直连 | 只能管理「服务端三层可达且 22 端口放行」的机器 |
| 批量绑定整批共用一套凭据 | `routes/nodes.js` `/batch` | 不同网段、不同机房的账号口令不同时，只能拆成多批 |
| 采集为「服务端到节点的长连接 + 5s 周期」 | `collector.js` `startMonitor()` | 跨公网/高延迟链路下，心跳开销与超时判定需要重新标定 |

### 1.2 要解决的业务问题

> 系统终究要管理**不同网段**的 GPU 服务器。用户在管理端无法直连这些机器时，系统必须仍能完成：**实时监控 / 进程明细 / 管理员终止 / 审计留痕** 四件事。

典型真实场景：

- 同一园区不同 VLAN（`10.10.x`、`10.20.x`），三层路由可达但需放行策略；
- 机房 A 的 GPU 机器在 `192.168.1.0/24`，机房 B 也是 `192.168.1.0/24`（**地址重叠**）；
- 机器在 NAT 之后，只允许出站、不允许管理端入站；
- 必须经堡垒机（Jump Host）才能登录设备；
- 跨公网 / 跨地域专线，延迟 30–200ms；
- 部分网段有单向网闸或严格白名单，只允许特定方向的 HTTPS。

### 1.3 目标

| 编号 | 目标 |
|---|---|
| G1 | 只要存在**任一可行通道**（直连 / 跳板 / VPN / 隧道 / 出站上报），系统就能接入该 GPU 节点 |
| G2 | 接入方式对上层功能透明：总览、下钻、终止、审计的行为与同网段一致 |
| G3 | 支持**地址重叠**：不同站点出现相同私有 IP 时互不覆盖 |
| G4 | 跨网段链路的失败可诊断：能定位到「DNS / TCP / SSH 认证 / GPU 命令 / 权限」哪一层断 |
| G5 | 安全边界清晰：凭据加密、主机指纹固定、最小权限、全链路审计 |
| G6 | 不引入 Kubernetes / Agent 之外的重量级依赖；Node.js 单机可部署 |

### 1.4 非目标（本期不做）

- 不做多管理端高可用集群（单管理端 + 数据备份即可）；
- 不做 GPU 作业调度、排队、镜像分发（沿用基线 PRD 的裁剪结论）；
- 不替换系统级监控（Grafana/Prometheus 若已有，仅做对接而非重建）；
- 不在本期实现自动发现网段内主机（扫描器不在范围）。

## 2. 网络场景与支持矩阵

| 场景 | 拓扑特征 | 现状 | 本期目标 | 采用方案 |
|---|---|---|---|---|
| **S1 同网段直连** | 管理端与 GPU 同二层/同子网 | ✅ 已支持 | 保持 | A 直连 |
| **S2 跨网段三层可达** | 不同 VLAN/子网，路由可达，22 端口放行 | ✅ 已支持（只要可达） | 保持 + 诊断增强 | A 直连 |
| **S3 需经跳板机** | 只能先登堡垒机，再由堡垒机访问 GPU | ❌ 不支持 | ✅ 支持（含两级） | B 跳板级联 |
| **S4 节点在 NAT 后** | 节点无公网/无入站端口，仅可出站 | ❌ 不支持 | ✅ 支持 | D 反向隧道 / E 出站 Agent |
| **S5 严格白名单/单向** | 仅允许出站 HTTPS，禁 SSH 入站 | ❌ 不支持 | ✅ 支持（HTTPS 出站） | E 出站 Agent |
| **S6 地址重叠** | 多个站点都用 `192.168.1.x` | ❌ 会互相覆盖 | ✅ 支持 | 唯一 ID 重构（FR-N1） |
| **S7 网段内机器不能装软件** | 只能从一台网关机横向 SSH | ❌ 不支持 | ✅ 支持 | F 站点网关（Agent 的变体） |

> 结论：**没有任何单一方案能覆盖全部场景**。本期采用「**一个节点一种接入方式**」的可插拔模型，按场景组合。

## 3. 技术方案调研

### 3.1 方案 A：SSH 直连（现状，保留）

- **原理**：服务端用 `ssh2` 直连 `host:port`，持久连接 + 5s 执行一次命令。
- **网络要求**：服务端到节点三层可达，目标端口放行，节点 SSH 服务可用。
- **优点**：零新增组件；延迟最低；终止通道与采集通道天然一致。
- **限制**：NAT 后不可用；地址重叠无解；跨公网直接暴露 22 端口有安全风险。
- **结论**：作为默认方式保留，补「自定义端口 + 显式声明接入方式 + 连通性分层诊断」。

### 3.2 方案 B：跳板机 SSH 级联

ssh2 官方 README 的 *Connection hopping* 示例给出了标准做法：在第一跳连接就绪后调用 `forwardOut()` 打开到目标 `host:22` 的 TCP 通道，再把这个通道作为第二跳的 `sock` 传入 `connect()`：

```js
conn1.on('ready', () => {
  conn1.forwardOut('127.0.0.1', 12345, '10.1.1.40', 22, (err, stream) => {
    conn2.connect({ sock: stream, username: 'user2', password: 'password2' });
  });
}).connect({ host: '192.168.1.1', username: 'user1', password: 'password1' });
```

- **网络要求**：只需服务端可达跳板机；跳板机可达目标节点的 SSH 端口。
- **优点**：改动集中在 `ssh.js`（新增 `jump` 配置与 `sock` 组装），采集/终止代码零改动；支持两级跳板覆盖绝大多数堡垒机场景；跳板机连接可跨节点复用（连接池）。
- **限制**：跳板机成为单点；需要额外一套跳板机凭据；堡垒机若禁止 `direct-tcpip` 转发则不可用（需实测）。
- **设计要点**：跳板机凭据独立加密存储、可被多节点引用（凭据配置档）；跳板连接失败要能与「目标节点失败」区分，否则诊断会误判。

### 3.3 方案 C：VPN 覆盖网（WireGuard / Tailscale / ZeroTier）

- **原理**：在管理端与各站点之间建立加密覆盖网，所有节点获得互通的三层地址，系统**代码零改动**，只是把节点地址填成覆盖网 IP。
- **Tailscale 的 Subnet Router** 能力值得单独说明：把一个能运行客户端的网关机接成子网路由器后，整个物理子网（包括打印机、老设备、不能装客户端的 GPU 机器）都能被覆盖网访问，且这些设备不占用设备配额。官方文档明确其定位是「无法安装客户端的设备/整段网络的接入网关」。
- **优点**：与业务系统解耦，故障域清晰；一次配置长期受益；天然解决「跨机房互联」；对地址重叠可用「不同 tailnet / 不同站点命名空间」规避。
- **限制**：需要网络侧投入（防火墙放行 UDP、部署网关机、分发包）；WireGuard 需要至少一端可达或依赖中继；企业内网审批流程可能较长；纯内网隔离环境可能不允许。
- **结论**：**强烈建议作为跨机房的基础设施方案**，但不应成为系统的硬依赖（系统必须自己也能处理跳板/Agent）。

### 3.4 方案 D：反向 SSH 隧道

- **原理**：节点侧常驻 `ssh -N -R 20022:127.0.0.1:22 user@管理端`（配 `autossh` 或 systemd 守护），管理端把该节点登记为 `127.0.0.1:20022`。
- **优点**：无需改网络策略（只要节点能出站 22）；实现成本最低；适合临时救急。
- **限制**：每个节点一个转发端口，端口管理易乱；节点重启后需自愈；**当前代码会把 `127.0.0.1` 判为本机直连**，必须先替换为显式接入方式；无法区分「谁连上来的」，审计溯源弱。
- **结论**：作为兜底手段写入文档，不建议作为主方案。

### 3.5 方案 E：出站 Agent 上报（推荐长期方案）

- **原理**：在 GPU 节点侧常驻一个轻量 Agent（Node 单文件 / 系统服务），**由节点主动向管理端建立出站 HTTPS/WSS 长连接**，本地执行采集命令，按周期上报快照；终止指令由管理端下发，Agent 执行后回执。
- **优点**：
  - 彻底穿透 NAT / 严格白名单（只需出站 443）；
  - 跨公网延迟下比「5s 一次的 SSH 会话」开销更低（长连接 + 批量上报）；
  - 天然支持大规模（服务端不维护 N 条 SSH）；
  - 可本地缓冲，网络抖动不丢数据；终止有明确回执，可靠性优于「断线即未知」。
- **限制**：需要在每台节点部署并升级；管理端必须暴露 HTTPS 入口；信任模型变化（节点可伪造上报，需令牌/mTLS 与指令签名）；逆向「拉取」变「推送」后，`state.js` 的采集口径要改为接收上报。
- **设计要点**：一次性注册令牌 → 换取长期凭据；心跳与指标分离；指令带 `requestId` 保证幂等；Agent 版本上报以支持滚动升级。

### 3.6 方案 F：站点网关（Site Gateway）

- **原理**：每个站点部署 1 台网关机（跑 Agent），由它横向 SSH 本网段的多台 GPU 机器，聚合后统一上报中心。
- **适用**：GPU 机器不能装软件、但网段内有一台可出站的 Linux/Windows 机器；或已有堡垒机可复用。
- **优点**：节点零安装；中心只与少量网关建连；地址重叠在站点维度天然隔离。
- **限制**：网关是单点；网关需持有本网段所有节点的凭据（信任集中，需强保护）。

### 3.7 方案对比

| 维度 | A 直连 | B 跳板级联 | C VPN 覆盖网 | D 反向隧道 | E 出站 Agent | F 站点网关 |
|---|---|---|---|---|---|---|
| 穿透 NAT | ❌ | ❌ | ✅ | ✅ | ✅ | ✅ |
| 严格白名单 | ❌ | ❌ | ⚠️ 需放行 | ⚠️ 需出站 22 | ✅ 仅 443 | ✅ 仅 443 |
| 解决地址重叠 | ❌ | ❌ | ⚠️ 需规划 | ⚠️ 需映射 | ✅ | ✅ |
| 系统改动量 | 无 | 小 | **无** | 小 | **大** | 中 |
| 网络侧投入 | 无 | 中 | **大** | 小 | 中 | 中 |
| 实时性 | 最好 | 好 | 好 | 好 | 好（长连接） | 好 |
| 终止可靠性 | 好 | 好 | 好 | 中 | 最好（回执） | 好 |
| 节点需装软件 | 否 | 否 | 是/网关 | 是（隧道） | **是** | 否 |
| 大规模（>100 节点） | 差 | 中 | 好 | 差 | **最好** | 好 |
| 运维复杂度 | 低 | 中 | 中高 | 中 | 中高 | 中 |

### 3.8 推荐路线（分阶段）

| 阶段 | 内容 | 覆盖场景 | 理由 |
|---|---|---|---|
| **P0** | 显式 `accessMode` + 唯一 ID/站点 + 跳板级联 + 分层诊断 + 分段凭据 | S1–S3、S6 | 纯软件、不依赖网络改造，覆盖最常见的「堡垒机 + 多 VLAN + 地址重叠」 |
| **P1** | 出站 Agent（含注册、心跳、指令回执） | S4、S5 | 解决 NAT 与严格白名单，是规模化的必要前提 |
| **P2** | 站点网关模式 + 调度优化（自适应周期/退避/并发上限） | S7、大规模 | 适配「节点不能装软件」与百级规模 |
| 并行建议 | VPN 覆盖网（Tailscale / WireGuard）作为基础设施 | 多机房 | 系统零改动即受益，但**不作为依赖** |

## 4. 功能需求（FR）

### FR-N1 节点唯一标识与站点维度（P0，前置）

- 节点主键由 `ip` 改为不可变 `nodeId`（UUID 或 `site + address` 派生），`address` 仅作连接参数。
- 节点新增字段：`site`（站点/网络域，**必填**，默认 `default`）、`accessMode`（`direct` / `jump` / `agent` / `gateway`）。
- 地址重叠时，UI 一律以「`站点名` / `别名` / `IP:端口`」三元组展示；仅显示 IP 视为缺陷。
- 迁移：启动时扫描旧 `nodes.json`，为每条记录补 `nodeId`、`site='default'`、`accessMode='direct'`，并原子写回；旧文件备份为 `nodes.json.bak`。
- 影响面（必须同步改造，否则出现「键不一致」bug）：`store` 的键、`state.snapshots`、`collector.conns`、`failCount`、SSE 事件里的节点标识、REST 路由 `/:nodeId`、审计 `target` 字段。

### FR-N2 接入方式显式声明（P0）

- 绑定/新增节点时必须选择接入方式，不再由 IP 猜测本机直连。
- `127.0.0.1` 只有在 `accessMode=direct` **且** 勾选「本机节点」时才走 `LocalNode`；`accessMode=tunnel` 的 `127.0.0.1:20022` 必须走 SSH。
- 列表页展示接入方式徽章（直连 / 跳板 / 隧道 / Agent）。

### FR-N3 跳板机管理（P0）

- 支持配置**最多两级**跳板（跳板 A → 跳板 B → 目标），每级独立 `host/port/用户名/凭据`。
- 跳板可作为**独立实体**被多个节点引用（避免逐节点重复录入）；跳板凭据独立 AES 加密、接口永不回显。
- 绑定验证时逐步上报进度：`跳板1连通 → 跳板1认证 → 跳板2连通 → 目标端口可达 → 目标认证 → GPU 采集 → 登记`。
- 跳板转发失败（如堡垒机禁用 `direct-tcpip`）应给出**明确错误码**，而不是笼统的「网络不可达」。
- 跳板连接按 `jumpId` 复用（同一跳板下多节点共享第一跳连接），降低堡垒机会话数。

### FR-N4 连通性分层诊断（P0）

新增「诊断」动作，逐层返回结果，任何一层失败即停止并给出修复建议：

| 层 | 检查项 | 失败提示示例 |
|---|---|---|
| L1 名称解析 | `address` 是否可解析 | 「无法解析主机名」 |
| L2 TCP 可达 | 目标端口（或跳板端口）是否可建连 + RTT | 「TCP 超时（15s），请检查路由/安全组」 |
| L3 SSH 认证 | 用户名/密码/密钥 | 「认证失败」vs「主机指纹不匹配」 |
| L4 命令执行 | `echo ok` / 平台探测 | 「已登录但无法执行命令（受限 shell）」 |
| L5 GPU 可用 | `nvidia-smi` 返回与解析 | 「nvidia-smi 不存在 / 驱动未加载」 |
| L6 权限 | 能否读取他人 `/proc`、能否 `kill` | 「无法读取其他用户进程，请提升权限」 |

- 诊断结果需可复制（运维贴给网络/系统同事）。
- 每层记录耗时，供 WAN 性能评估。

### FR-N5 出站 Agent（P1）

- **注册**：管理员在页面生成一次性注册令牌（有效期默认 24h，可撤销），Agent 首次启动用它换取长期凭据。
- **连接**：Agent 主动出站连接管理端 `443`（HTTPS/WSS），断线指数退避重连（1s→2s→…→60s 封顶，带抖动）。
- **上报**：心跳（轻量，默认 10s）+ 快照（默认 5s，可配）；快照结构与现有 `snapshot` 保持一致，避免上层改造。
- **指令**：管理端下发 `kill`，带 `requestId`；Agent 幂等执行并回执 `grace/forced/gone/failed`；超时未回执标记「结果未知」并写入审计。
- **缓冲**：断线期间本地保留最近 N 个快照（环形，默认 12 个），恢复后不必补传全部（仅补最后一次）。
- **版本**：上报 Agent 版本与平台，支持后续滚动升级。
- **安全**：长期凭据可轮换；支持 mTLS；严禁 Agent 接受「任意 shell 命令」类指令（仅白名单动作 + 固定命令模板），防止管理端被攻破后横向提权。

### FR-N6 凭据配置档（P0）

- 抽象「凭据配置档」：`{名称, 用户名, 密码/密钥, 适用站点}`，可被批量绑定复用。
- 批量绑定支持「每行 `IP` 后可选附加凭据档名」，实现一次粘贴、多套凭据；默认仍整批共用。
- 凭据更新时，引用该档的节点自动重验（沿用现有 `node_cred_update` 审计）。

### FR-N7 地址重叠与展示（P0）

- 重复检测口径由「IP 重复」改为「`site + IP` 重复」；跨站点同 IP 允许共存。
- 总览页 GPU 卡片必须显示 `站点 / IP`（本期已加 IP，需扩展为站点维度）。
- 节点删除、终止进程等确认弹窗必须带站点，避免同 IP 误操作。

### FR-N8 采集调度与 WAN 优化（P0/P2）

- 每节点可配置采集周期（站点级默认值 + 节点覆盖），WAN 站点可放宽到 10–30s。
- 全局并发上限（默认 32），避免 100 节点同时 SSH 打满文件描述符与带宽。
- 失败退避：连续失败从 `5s → 10s → 20s → 40s`（上限 60s），恢复后回到正常周期；与现有「连续 3 次失败转离线」规则并存（退避只影响尝试频率）。
- 周期加入 ±10% 抖动，避免同一秒全员并发。
- 跨网段 RSS/带宽预算：给出「N 节点 × 周期 × 单次字节数」估算表。

### FR-N9 离线判定与告警（P0）

- 离线阈值按接入方式区分：直连 3 次失败；Agent 用「心跳超时」（默认 30s）；跳板链路额外容忍 1 次。
- 告警文案需含站点与接入方式，例如「站点 A / 10.10.1.21（跳板 bastion-1）已离线 45s」。
- Agent 离线与「节点关机」需可区分（Agent 主动 `bye` 消息 vs 静默超时）。

### FR-N10 终止动作跨网段可靠性（P1）

- 全部终止指令携带 `requestId`，重复下发不重复执行（幂等）。
- 跳板/Agent 通道下，若指令发出后连接中断，状态置「结果未知」，并在下一次采集时以「PID 是否仍存在」做**事后校正**。
- 终止审计新增字段：`accessMode`、`via`（跳板名/Agent id）、`requestId`。

### FR-N11 审计与安全（P0）

- 新增审计动作：`node_diag`（诊断）、`jump_create` / `jump_update` / `jump_delete`、`agent_enroll`、`agent_revoke`、`agent_offline`、`site_create`。
- 节点凭据、跳板凭据、Agent 令牌三者分离存储、独立加密密钥域（或同密钥不同前缀）。
- SSH 主机指纹固定（`hostVerifier` 首次信任 + 后续比对），指纹变更必须显式确认并审计。
- 管理端对外暴露 Agent 入口时，必须 HTTPS；建议前置反向代理做限流与 IP 白名单。

### FR-N12 站点与拓扑视图（P1，非阻塞）

- 节点管理页按站点分组折叠；总览页可按站点筛选。
- 提供「站点连通性概览」：每站点在线数/离线数/平均 RTT/失败率。
- 不在本期做图形化拓扑连线（成本高、收益低）。

## 5. 非功能需求

| 类别 | 要求 |
|---|---|
| 规模 | 单管理端支持 ≥ 200 节点（Agent 模式）；直连模式建议 ≤ 50 节点 |

## 8. UI / 交互要点

1. **绑定流程分步化**：选择接入方式 →（跳板模式下选跳板机）→ 填地址与凭据 → 连通性预检 → 提交。避免「一次表单塞 12 个字段」。
2. **接入方式徽章**：节点列表与 GPU 卡片均显示（直连 / 跳板 / 隧道 / Agent），故障时一眼看出问题在通道还是节点。
3. **诊断对话框**：六层结果用「通过/失败/耗时」三列，失败层给出建议；一键复制。
4. **站点筛选**：总览顶部新增站点下拉；节点管理页按站点分组。
5. **地址重叠提示**：输入 `site + IP` 已存在时提示「该站点下已存在此 IP」，但不阻止跨站点同 IP。

## 9. 里程碑与验收标准

### M1（P0）显式接入方式 + 唯一 ID + 跳板级联 + 诊断

验收用例：

1. 在相同 `192.168.1.10` 的两个站点各绑定一台节点，两台同时在线、互不覆盖；总览各显示 1 张卡。
2. 通过一级跳板绑定 GPU 节点，四步进度条显示「跳板认证 → 目标认证 → GPU 采集 → 登记」并成功。
3. 跳板机密码错误 → 诊断显示「L3 跳板认证失败」，不误报为目标节点不可达。
4. 目标节点 `nvidia-smi` 不存在 → 诊断显示「L5 GPU 不可用」，其余层为通过。
5. 跳板下线的节点终止进程 → 提示「通道不可用」，审计记录失败原因，不产生假成功。
6. 迁移旧 `nodes.json` 后，原节点全部在线，`nodes.json.bak` 存在。

### M2（P1）出站 Agent

验收用例：

1. NAT 后的节点安装 Agent 并用一次性令牌注册成功，管理端无反向上连该节点。
2. Agent 上报的显存/进程数据与在节点本地执行 `nvidia-smi` 一致（人工比对）。
3. 管理端断网 60s 后恢复，Agent 自动重连（指数退避生效），期间页面显示离线、恢复后自动在线。
4. 页面终止进程 → Agent 回执 `grace/forced`，审计含 `requestId` 与 `agentId`。
5. 撤销令牌后，新 Agent 无法注册；已注册 Agent 仍可用（或按策略一并失效，需明确）。

### M3（P2）站点网关 + 调度优化

1. 一台网关机代理 8 台不可安装软件的 GPU 机器，中心只建立 1 条出站连接。
2. 200 节点规模下，采集周期抖动 ±10%，全局并发不超过配置上限，CPU/内存占用可接受。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 唯一 ID 重构波及全链路 | 键不一致导致数据错乱 | 一次性改完 + 启动迁移校验 + 回归测试覆盖绑定/采集/终止/删除 |
| 堡垒机禁用 `direct-tcpip` | 跳板方案失效 | 绑定前诊断探测该能力；失败时引导改用 VPN/Agent |
| Agent 成为攻击面 | 节点伪造数据或提权 | 令牌 + mTLS + 指令白名单 + 固定命令模板 + 审计 |
| 跨公网暴露管理端 | 登录爆破 | HTTPS + 反向代理限流 + 现有登录锁定策略 + 建议 IP 白名单 |
| 地址重叠被运维忽略 | 误操作到错误机器 | 站点维度必填 + UI 强制三元组展示 + 确认弹窗带站点 |
| WAN 抖动导致频繁离线告警 | 告警疲劳 | 按接入方式区分阈值 + 退避 + 告警收敛（同节点 5 分钟内只告警一次） |

## 11. 待用户确认的开放问题

在进入编码前，需要明确以下事实（直接决定 P0 的范围）：

1. **网络可达性**：管理端所在的机器，能否直接 `ping` / `ssh` 到各 GPU 服务器的 IP？哪些网段需要额外放行？
2. **是否存在堡垒机**：如果有，堡垒机类型（JumpServer / 自研 / 云厂商）、是否允许 TCP 转发、是否支持多级跳转？
3. **节点是否允许安装常驻程序**：能否在 GPU 机器上跑一个后台服务（Agent）？Windows 节点是否同样允许？
4. **是否允许出站**：节点能否访问管理端的 443？是否只能单向出站？
5. **是否有地址重叠**：不同机房的私网地址是否重复（例如都用 `192.168.1.0/24`）？
6. **规模**：预计节点数与显卡数量上限；各站点大致分布。
7. **VPN 可行性**：是否已有 WireGuard / Tailscale / 专线等基础设施？能否接受新增？
8. **实时性要求**：跨网段节点是否必须 5s 刷新，还是 10–30s 可接受？

## 12. 附录

### 12.1 术语

| 术语 | 说明 |
|---|---|
| 站点（Site） | 一个独立的网络域/机房，站内地址可重复，站间由路由或隧道互通 |
| 接入方式（accessMode） | 管理端到达该节点的通道类型：direct / jump / agent / gateway |
| 跳板机（Jump Host） | 可被管理端直连、并能继续访问目标节点的中间主机（堡垒机） |
| 出站 Agent | 运行在节点侧、主动向管理端建立连接并上报数据的常驻进程 |
| 站点网关（Site Gateway） | 代理一个站点内多台节点上报的中间主机 |

### 12.3 与基线 PRD 的关系

本文档是对基线 PRD「FR-1 节点接入」的扩展，不改变以下既有口径：

- 空闲判定阈值 500MB、采集周期默认 5s、终止宽限期默认 30s；
- 两段式终止、PID 二次确认、同进程 1 分钟 3 次重试上限；
- 审计留痕与管理员权限模型。

新增内容仅涉及「管理端如何到达节点」这一层，上层功能语义保持不变。
